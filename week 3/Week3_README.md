## 4. Theoretical learning

### 4.1 Endpoint Detection and Response (EDR)

EDR continuously monitors endpoint activities, collects security
telemetry and helps security analysts investigate suspicious behaviour.

Key concepts include:

-   Monitoring processes and application execution.
-   Detecting suspicious network connections.
-   Identifying unauthorised file modifications.
-   Investigating unusual user activities.
-   Supporting incident response through endpoint visibility.

EDR provides more detailed endpoint visibility than traditional
antivirus, which primarily focuses on detecting and preventing malicious
software.

### 4.2 Windows Sysmon

Sysmon (System Monitor) is a Windows Sysinternals tool that records
detailed system activities in Windows Event Logs.

  Event ID   Event                SOC application
  ---------- -------------------- -----------------------------------------
  1          Process Create       Monitor process execution
  3          Network Connection   Identify suspicious network connections
  11         File Create          Detect suspicious file creation
  13         Registry Value Set   Monitor registry modifications
  22         DNS Query            Investigate suspicious DNS requests

Sysmon provides information such as process names, command-line
arguments, usernames, network addresses and file paths.

### 4.3 Linux auditd

auditd is the Linux auditing framework used to monitor and record
security-related activities.

It can help analysts investigate command execution, user authentication,
file access, privilege-related activities and system configuration
changes.

  Event type   Purpose
  ------------ ---------------------------------
  EXECVE       Records command execution
  USER_LOGIN   Records user login activity
  USER_AUTH    Records authentication attempts

auditd focuses on security auditing and detailed event records, while
syslog collects general system and application messages.

### 4.4 Snort IDS/IPS

Snort is an open-source network intrusion detection and prevention
system. It analyses network packets and compares them against configured
rules to identify suspicious traffic.

-   **IDS mode:** Monitors network traffic and generates alerts.
-   **IPS mode:** Can actively block or prevent suspicious traffic when
    deployed inline with suitable configuration.

Common Snort rule options include:

  Option      Purpose
  ----------- ------------------------------------------------------
  msg         Defines the alert message
  sid         Identifies the rule
  rev         Defines the rule revision
  flags       Matches TCP flags
  flow        Specifies traffic direction or connection state
  threshold   Controls alert frequency in compatible rule versions
  classtype   Classifies the detected activity

### 4.5 Signature-based and anomaly-based detection

-   **Signature-based detection:** Identifies activity using known
    patterns, signatures or predefined rules. An example is a Snort rule
    matching specific TCP SYN traffic.
-   **Anomaly-based detection:** Identifies behaviour that deviates from
    an established baseline. An example is an unusual increase in
    network connections from a workstation.

Both approaches help SOC analysts identify suspicious activity.

### 4.6 MITRE ATT&CK T1046

T1046 is **Network Service Discovery**. It describes adversary behaviour
involving discovery of network services, systems and open ports.

An example is using Nmap to identify open ports and services on a target
machine. Snort rules can be mapped to MITRE ATT&CK techniques using
metadata and reference fields.

## 6. Advanced Snort rule -- MITRE ATT&CK T1046

**Status: Successfully completed**

An advanced rule was created to detect Nmap SYN scans and associate the
activity with MITRE ATT&CK T1046 -- Network Service Discovery.

The final rule was:

``` text
alert tcp any any -> $HOME_NET any (msg:"MITRE T1046 - Nmap SYN Port Scan Detected"; flags:S; detection_filter:track by_src, count 20, seconds 1; classtype:attempted-recon; metadata:mitre_technique T1046; reference:url,attack.mitre.org/techniques/T1046/; sid:1000004; rev:2;)
```

### 6.1 Rule explanation

  Component          Explanation
  ------------------ ---------------------------------------------------
  alert tcp          Generates an alert for matching TCP traffic
  flags:S            Matches TCP SYN packets
  detection_filter   Controls detection frequency
  track by_src       Tracks packets by source IP
  count 20           Uses a threshold of 20 packets
  seconds 1          Evaluates the threshold over one second
  classtype          Classifies the activity as reconnaissance-related
  metadata           Maps the rule to MITRE T1046
  reference          Provides the official MITRE ATT&CK reference
  sid                Identifies the rule as 1000004
  rev                Identifies the current rule revision as 2

### 6.2 Compatibility issue and solution

The original task supplied the Snort 2 `threshold` keyword. Snort
3.13.2.0 rejected it with an unknown rule keyword error.

The rule was adapted to use Snort 3's `detection_filter` syntax. The
rule revision was increased to 2.

After this change, the configuration successfully validated with zero
warnings. The updated validation showed 223 rules loaded.

### 6.3 Nmap SYN scan testing

The following command was executed from Kali Linux against the Ubuntu
lab VM:

``` bash
sudo nmap -sS -p 1-1000 192.168.50.5
```

Snort successfully detected the activity and generated multiple alerts:

``` text
MITRE T1046 - Nmap SYN Port Scan Detected
```

Observed traffic:

-   **Source IP:** 192.168.50.4 (Kali)
-   **Destination IP:** 192.168.50.5 (Ubuntu)
-   **Rule SID:** 1000004
-   **Rule revision:** 2
-   **Classification:** Attempted Information Leak
-   **MITRE technique:** T1046

The advanced rule successfully detected Nmap SYN-scan activity within
the lab network.

The rule uses `any` as its source selector rather than `$EXTERNAL_NET`
because Kali and Ubuntu are both within the configured HOME_NET subnet.
Using `$EXTERNAL_NET` would have excluded the internal Kali scanner.
